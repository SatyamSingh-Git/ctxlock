**Date:** 2026-11-13 · **Where:** two scratch repositories on GitHub, made for this with Satyam's OK:
- [`ctxlock-scratch-org`](https://github.com/SatyamSingh-Git/ctxlock-scratch-org), public;
- `ctxlock-scratch-web`, private.

**Plans:** [Plan 8](../superpowers/plans/2026-11-12-ctxlock-diagnose.md) (`--open`, D87) and [Plan 6](../superpowers/plans/2026-11-10-ctxlock-propagation.md) (the sync workflow, D68).

**Question:** both had run only against a stand-in for `gh`. Do they work against GitHub itself?

**Answer:** yes, after one fix the run found. The sync workflow could leave a branch with no pull request, forever. It is fixed and tested (`9e35bfc`).
- **`--open`:** filed one issue, then updated that same issue, and reopened it after it was closed.
- **The workflow:** opened one pull request, updated it when the upstream fixed its rule, and left it alone when nothing changed.

## The repositories

- **`ctxlock-scratch-org`:**
  - **What it holds:** its rule says "Install packages with npm install" while its `package.json` names pnpm, the planted miss of Plans 8 and 9.
  - **Why it is public:** a private upstream needs a token that can read it, saved in the consumer as `CTXLOCK_UPSTREAM_TOKEN`. Saving the author's own `gh` token there would give the workflow far more than it needs. It holds a toy rule and nothing else.
- **`ctxlock-scratch-web`:** takes that rule through `upstream:` in its `ctxlock.yaml`. It runs `templates/ctxlock-sync.yml`, with `CTXLOCK_REF` pinned to a ctxlock commit, as the guide advises.
- **The session:** planted in a local clone of the org repository, as before. The issue holds no text from it.

The script that builds all of this, `livegh.mjs`, is kept in the session's scratchpad.

- **The body:** the proposal, and nothing else:
  - the marker line;

- **Search lag:** by run 2, GitHub's search had already indexed #1, so the fallback to the 100 latest issues was not needed this time. The unit test covers the case where search hasn't caught up.

## The sync workflow

| Run | Before it | Result |
|---|---|---|
| 1 | a new repository, Actions not allowed to create pull requests | Sync passed and pushed `ctxlock/sync`. Then "GitHub Actions is not permitted to create or approve pull requests", and the job failed |
| 2 | the setting turned on | Exit 0, "The pull request already has this.", and **no pull request**. This is the bug below |
| 3 | the template fixed | Pull request #1, with the rule, `ctxlock.lock` and an `AGENTS.md` that loads it |
| 4 | the upstream committed the fix from issue #1 with its probe (`731a1c8`) | #1 updated: the rule now names pnpm, and the lock pins `731a1c8`. Still one pull request |
| 5 | nothing new upstream | "The pull request already has this.", and the branch didn't move |

**The bug:**
- **The template's check:** it skipped a push when the branch `ctxlock/sync` already held the same files, so that an open pull request would keep its approvals.
- **What went wrong:** after run 1, the branch held them, but no pull request existed. Every later run would have skipped, and no reviewer would ever see the change.
- **Another way in:** closing the pull request had the same effect.
- **The fix:** the check now applies only when a pull request is open. The stand-in test had never had a branch without one.

**The setting:** a new repository has "Allow GitHub Actions to create and approve pull requests" off. The guide already said it must be on. It now also says what happens without it, and gives the `gh api` command that turns it on.

## Afterwards

`ctxlock outcomes` on the org clone found the fix shipped in `731a1c8`, 9 minutes after the planted signal. "Reached" was empty, as it should be: the consumer's lock is on its pull request, not yet merged, and `--locks` was not given.

Both repositories are kept, so the issue and the pull request can be read. They hold nothing but the fixture.
